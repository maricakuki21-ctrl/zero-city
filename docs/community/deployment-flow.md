# 贡献、测试发布与公告分工

## 代码流程

1. 提交 PR，前端与后端检查自动运行。
2. 维护者确认范围后开启 GitHub 自动合并，检查不通过时不得合并。指定目录内的小文档改动由机器人直接处理。
3. 合并后的 main 再构建一遍，确保部署的是合并结果，而不是旧分支产物。
4. 只有当前 main 的成功构建能进入社区测试站；外部 PR 不拿部署凭据。
5. 测试站记录提交 SHA。启动或健康检查失败时恢复上一版程序与更新前的测试数据库。

测试站的 `/community-build.json` 提供部署提交与构建编号。入口见 TESTING.md。正式服不参加这条自动更新链路。

## 公告权限单独处理

提交公告建议、发布站内公告、修改代码、发布正式版本是不同动作。
不能为了发布公告给人开总管理员权限，也不能因为能提交公告就允许改支付、用户或部署配置。

当前公告仍使用站内原有管理员接口。公告发布者的身份与授权方式待站长确认，尚未向任意社区用户开放直接发布权限。

## 失败时

- 自动检查失败：PR 保持未合并。
- 旧提交排队到达：跳过，不覆盖更新的 main。
- 文件包不完整或路径异常：拒绝安装，当前服务不动。
- 新版本无法启动：恢复上一版与测试数据库快照，保留明确失败记录。
- 临时 HTTPS 隧道故障：单独检查入口服务，不以应用健康状态代替公网验证。

这里承诺的是可检查、可回退的流程，不是所有业务功能都不会有缺陷。发现问题仍需提交复现步骤。
